## P1. 再行動ルールの改定(最重要)

**回転攻撃を廃止し、回転と攻撃を分解して個別に値付けする。**

| 行動 | コスト | 制限 |
|---|---:|---|
| 回転 | **1**(一律・コスト帯によらない新定数) | 1ターン1回 = **90度まで** |
| 攻撃 | `commandCost`(現行の 2/2/2/3/3/3 をそのまま流用) | 1ターン1回 |
| 順序 | **回転 → 攻撃 のみ** | **攻撃したらその式神の再命令は終了。攻撃後の回転は不可** |

### 価格の変化(参考)

| | 旧 | 新 |
|---|---:|---:|
| 回転のみ(C2〜C4) | 2 | **1** |
| 回転のみ(C5〜C7) | 3 | **1** |
| 攻撃のみ | 2〜3 | 2〜3(据え置き) |
| 回して殴る | 2〜3(回転攻撃1アクション) | 3〜4(2アクション) |

### 実装上の注意

- `commandCost` は**攻撃のコスト**として引き続き使う。回転には使わない
- 回転コストは**新しい定数**として持たせる(値1)
- **攻撃後にその式神が回転できない**ことを状態として持つ必要がある。旧来の「回転枠/攻撃枠」より制約が強い
- **AI Lv1〜7すべて**の行動列挙とコスト計算を見直す。特に旧「回転攻撃」を1手として扱っていた箇所
- RULE_SPEC.md の該当箇所も更新する

### 帰結

**盤上の式神は1ターンに180度回れない**(召喚時のみ向き自由)。これは意図した仕様であり、術式〈旋〉の存在価値の根拠になっている。

## P2. 効果DSL拡張: 「連なっている味方の数」

### 何が足りないか

現行DSLで書けるもの・書けないものを実測した結果、**「盤上で連なっている味方の数を数える」語彙が無い**ことが最大の制約と判明した。

これ1つで、チームの中核コンセプト(カードの並べ方でシナジーを得る「戦術デッキ」)が丸ごと解禁される。

### 現行語彙(確認済み)

```json
{"type":"static","appliesTo":{"all":{"side":"ally","area":"adjacent_self"}},
 "modifier":{"kind":"damage","direction":"taken","delta":-1}}
```

- `appliesTo`: `self` / `{all:{side, area, other}}`
- `area`: `board` / `adjacent_self` / `attack_range` / `adjacent_of`
- `while`: `{cellAttribute: "yin"}`
- `modifier.kind`: `stat`(atk/hp/lifeValue) / `damage` / `command_cost` / flag
- `duration`: `end_of_turn` のみ

### 追加してほしいもの

**modifier の値を、盤面の数え上げに比例させられるようにする。**

```json
{"kind":"stat","stat":"atk","perCount":{"side":"ally","area":"connected_self","other":true},"delta":1}
```

- `connected_self` — **自分と上下左右で連結している味方の集合**(自分を含まない。連結は再帰的にたどる)
- `perCount` — 指定した集合の数 × `delta` を修正量とする
- 併せて `divisor`(例: 2体ごとに+1)を指定できると `鉄壁の陣` が書ける

**最小限でよい。** `connected_self` の数え上げと `perCount` があれば目的は達する。命名や構造は実装しやすい形に変えて構わない。

### 検証

- 連結が再帰的にたどれること(A-B-C と並んでいれば A から見て2体)
- 斜めは連結に含めない(RULE_SPECの隣接定義に従う)
- 盤面変化(召喚・撃破・移動)で数が正しく再計算されること
- AIの評価関数がこの修正値を正しく読むこと

## P3. 効果DSL拡張: マーカー「陰陽の徴」

チームで出ている中核アイデア。パッシブ効果を作りたいが、盤面にトークンが多いと認知負荷とコストが上がる——という課題に対する解。

### ルール

- 各プレイヤーは**陰マーカー1個・陽マーカー1個**を持つ(コンポーネントは全体で4個に固定)
- マーカーは**自分の式神にのみ**乗る
- **乗せる手段は式神自身の効果テキストに内蔵する。** マーカーを乗せる汎用カードは作らない
- 同じ色のマーカーを新たに乗せると、**後勝ちでそちらへ移動する**(元の式神からは外れる)
- マーカーが乗っている式神が盤面を離れたら、マーカーはどこにも乗っていない状態に戻る
- 効果はマーカー側ではなく、**各式神が「陽マーカーが乗っている限り〜」と参照する形**で持つ

盤面に1個しかないため、マーカー参照の式神を複数並べても恩恵を受けるのは1体だけになる。**これは欠陥ではなく「どれを立てるか」を選ばせるジレンマとして意図されている。**

### 必要な実装(最小限)

**状態**

```ts
markers: Record<PlayerId, { yin: UnitId | null; yang: UnitId | null }>
```

**action**

```json
{"action":"place_marker","marker":"yang","target":"self"}
```

同色が既にどこかに乗っていれば、そこから外して対象へ移す(後勝ち)。

**条件**

```json
{"type":"static","appliesTo":"self","while":{"marker":"yang"},
 "modifier":{"kind":"stat","stat":"atk","delta":1}}
```

`while.marker` は **その式神の所有者のマーカー**を見る。

**後始末**: 式神が盤面を離れたとき(撃破・移動先消失など)、その式神に乗っていたマーカーを `null` に戻す。

**UI**: プロトタイプなので最小でよい。盤上の式神に陰/陽のバッジが出れば足りる。

**AI**: 評価関数がマーカーの有無を読めるようにする。凝った評価は不要で、マーカー由来の修正値が正しく反映されていればよい。
