# Codex Task: うちのAI vs 正本AI(Lv7)の対戦

Status: 実行待ち
Date: 2026-07-25

前提資料: [MASTER-SOURCE.md](MASTER-SOURCE.md)、[baselines/ver1-baseline.md](baselines/ver1-baseline.md)

## 目的

本プロジェクトのAIを、正本エンジン上のエージェントとして実装し、**正本のCPU Lv7と対戦させる**。

副次的に得られるもの:

- うちのAIが正本のレベルラダー上でどこに位置するか
- **両エンジンの実装一致の検証**(§3の自己検証ゲート)

## 2. うちのAIを移植する

`clients/ai/src/agent.ts` に、新しいエージェント **`Lv-C`**(Claude/codex側のAI)を追加する。移植元は本プロジェクトの `scripts/explore-stat-curves.cjs`。

移植する要素:

| 要素 | 移植元の関数 |
|---|---|
| 召喚のスコアリング | `scoreSummon` |
| 攻撃のスコアリング | `scoreAttackAction` / `scoreAttackTarget` |
| 回転攻撃のスコアリング | `scoreRotateAttackAction` |
| 回転のスコアリング | `scoreRotation` |
| 通常手番の選択(グリーディ) | `simulateTurn` の非王手経路 |
| **王手返答の探索** | `findOracleReturnPlan`(深さ6、1ターン内の行動連鎖DFS、memo付き) |

**スコアの重みは変えずにそのまま移植すること。** 目的は「うちのAIの強さを測る」ことなので、改良は入れない。

正本のAPI(Command方式)の制約で解釈を変えざるを得なかった箇所は、**すべて実装ノートに記録**する。

## 3. 自己検証ゲート(重要・先に実施)

移植したLv-C同士を自己対戦させ、**本プロジェクトのシミュの数値を再現できるか**を確認する。

対照(`ver1-baseline.md`、vanilla-4・2000試合):

| 指標 | 本プロジェクトのシミュ |
|---|---:|
| 占拠勝ち | 11.8% |
| 生命勝ち | 88.0% |
| 平均ラウンド | 12.61 |
| 先手勝率 | 49.7% |
| 撃破/試合 | 16.93 |

**乖離が大きい場合(占拠/生命が10pt以上ずれる等)、両エンジンにまだ実装差があるか、移植が不正確**。原因を調べて報告し、対戦の数値はその注記つきで読むこと。

※ 乱数系列・シード生成が両者で異なるため、完全一致は期待しない。**傾向として一致するか**を見る。

## 4. 対戦の実行

すべて `--p0-packs vanilla-4 --p1-packs vanilla-4`、`--turn-limit 200`。

| ラン | 対戦 | 試合数 |
|---|---|---:|
| G0 | **Lv-C vs Lv-C**(§3の検証) | 200 |
| **G1** | **Lv-C vs Lv7**(先手後手を入れ替えて両方) | 各200 |
| G2 | Lv-C vs Lv5 / Lv-C vs Lv6 | 各100 |
| G3(参考) | Lv7 vs Lv7 | 200 |

## 5. 報告

- **Lv-Cの対Lv7勝率**(先手・後手別と合算)
- 各対戦の **占拠勝ち / 生命勝ち / 平均ラウンド / 撃破数**
- Lv-Cがラダー上のどこに位置するか(対Lv5/Lv6/Lv7の勝率から)
- §3の自己検証の結果

### 注目してほしい仮説

うちのAIは「**通常の着手はグリーディ(1手読み)、王手対応だけ深さ6で総当たり**」という非対称な構成である。ここから導かれる予測:

> **Lv-CはLv7に総合では負け越すが、占拠決着では非常に落ちにくい。試合は長引き、生命で決着する割合が高くなる。**

この予測が当たるかを明示的に検証してほしい。当たれば、本プロジェクトのシミュで観測された「占拠11.8% / 生命88%」に計測器の歪みが含まれることの直接証拠になる。
