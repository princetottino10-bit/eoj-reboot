Status: 実行待ち

性格: **計測器の校正**(構成の調整ではない)

前提資料: [current-spec-ver1.md](current-spec-ver1.md)、[baselines/ver1-baseline.md](baselines/ver1-baseline.md)、[MASTER-SOURCE.md](MASTER-SOURCE.md)

## 背景

本プロジェクトのシミュでVer1構成(vanilla-4)を測ると **占拠勝ち11.8% / 生命勝ち88.0%** となり、陣取りゲームとして機能していない。

ただしこの数値には**計測器の歪みが疑われる**:

- 本プロジェクトのAIは「通常の着手=グリーディ(1手読み)」「王手対応=1ターン内を深さ6で総当たり」という**非対称な構成**
- 王手の返し率90.6%はオラクル上限91.4%の99.1%に達しており、**防御がほぼ完璧**
- 完璧な防御相手に5マス制圧は成立しないため、削り合いに流れている可能性がある

正本には**実際に製品で使われるCPU Lv1〜7**が実装されている(`clients/ai`)。同じ構成をこのラダーで測れば、「どの強度で占拠決着がどれだけ起きるか」が製品として意味のある形で分かる。

## やること

正本リポジトリをローカルにクローンし、**既存のCLIをそのまま使って** Ver1構成(vanilla-4)をLv1〜7で総当たりする。**コードの改変は不要**。

### 1. 準備

```bash
gh repo clone fenril058/3x3_duel C:/Projects/3x3_duel
cd C:/Projects/3x3_duel
git remote set-url --push origin no-push   # 誤pushの防止(必須)

```

- **正本リポジトリへは絶対にpushしない**。実験はローカルのみ
- 環境が整わない場合(pnpm/Node/Nix)は、詰まった箇所を報告して中断してよい

### 2. 自己対戦の実行

```bash
cd clients/ai
node --experimental-strip-types src/cli.ts selfplay \
  --p0-packs vanilla-4 --p1-packs vanilla-4 \
  --levels 1,2,3,4,5,6,7 \
  --games 200 \
  --seed-base 20260702 \
  --turn-limit 200 \
  --verbose \
  --out ../../analysis/replays/ver1-lv-ladder.json
```

- レベルの順序対ごとに200試合(7×7=49条件 × 200 = 9,800試合)。時間がかかる場合は `--games` を100に落としてよい(その旨を記録)
- 続けて `aggregate` で統計を生成する(コマンドは `clients/ai/README.md` 参照)

### 3. 報告(本プロジェクト側に保存)

**同レベル対戦(Lv1対Lv1 〜 Lv7対Lv7)の対角成分**を主軸に、レベル別の表を作る:

| レベル | 占拠勝ち | 生命勝ち | 平均ラウンド | 先手勝率 | 撃破/試合(取れれば) |
|---|---|---|---|---|---|

加えて:

- **Lv3(製品のデフォルト)** と **Lv7(最強)** の値を明示
- 本プロジェクトのシミュ(`ver1-baseline.md`: 占拠11.8% / 生命88.0% / 平均12.61R / 先手49.7%)との対照
- 非対角成分(Lv差のある対戦)の勝率表が取れれば、レベル間の強さの階段も記録

## 考察(`handoff-analysis-kpi.md` の作法で)

**問い: 占拠11.8%という数値は、構成の性質か、計測器の歪みか。**

- レベルが上がるほど占拠勝ちが下がる傾向があるか(=防御力が上がるほど陣取りが成立しなくなるか)
- Lv7でも占拠勝ちが高いままなら、**本プロジェクトのAI固有の歪み**(グリーディな攻め+超人的な防御)が原因
- Lv7で占拠勝ちが低いなら、**構成の性質**として実在する問題

この判定によって次の方針が変わる:

- 構成の問題 → HP調整(H-B等)を進める
- 計測器の歪み → **KPIの目標帯をレベルとセットで再定義**し、どのレベルを基準に調整するかを決める(製品デフォルトのLv3が有力候補)
