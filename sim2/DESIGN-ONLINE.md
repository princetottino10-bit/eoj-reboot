# sim2 オンライン対戦 設計書

Status: 設計確定(実装待ち)
Date: 2026-09-13
設計: Fable / 実装: Opus
前提: `DESIGN.md`(エンジン)、`play/`(既存の人間 vs AI 対戦画面)

---

## 0. 目的

チームの3人(離れた場所にいる)が、**ブラウザだけで人間同士の対戦**をできるようにする。テストプレイの回数を増やし、ルール改訂のたびに集まらなくても手触りを確かめられるようにするのが目的。

**遊べるルールは 8/28ルールと 9/13テストルールの両方**。今チームが試しているのは 9/13ルールなので、そちらが使えないと意味がない。

## 1. 基本方針

| 項目 | 決定 | 理由 |
|---|---|---|
| 権威 | **サーバーが唯一のゲーム状態を持つ**。ブラウザは表示と入力だけ | 手札・山札の順番を相手に見せないため。ブラウザにゲーム状態を丸ごと渡すと、開発者ツールで相手の手札が見える |
| ルールの実装 | **既存の `sim2/src/` をサーバーでそのまま使う**。合法判定もサーバーで `isLegal` を呼ぶ | エンジンを1系統に保つ(既存方針) |
| 通信 | **Server-Sent Events(サーバー→ブラウザ)+ `fetch` POST(ブラウザ→サーバー)** | 外部依存ゼロで書ける。Node標準の `node:http` だけで実装できる。WebSocketサーバーはNode標準に無い |
| 依存 | **ゼロを維持** | 既存方針 |
| 部屋 | 6文字の部屋コードで作成・参加 | 招待はコードをLINEで送るだけ |
| 再接続 | 参加時に発行する**席トークン**をブラウザの `localStorage` に保存。リロード・回線断から同じ席に戻れる | 誤ってタブを閉じても試合が消えない |
| 永続化 | **メモリのみ**(サーバー再起動で部屋は消える) | テスト用途。ただし試合終了時に棋譜をJSONで `sim2/out/online/` に保存する |

## 2. 構成

```
sim2/online/
  server.ts        HTTP・SSE・API・静的配信。play/server.ts の型剥がし配信を流用(import)する
  rooms.ts         部屋の管理(作成・参加・席トークン・タイムアウト掃除)
  match.ts         1試合の進行。GameState を持ち、アクションを検証して適用し、イベントを配る
  view.ts          プレイヤー別の見える状態を作る(隠し情報を落とす)
  protocol.ts      ブラウザとサーバーでやり取りするメッセージの型
  lobby.html       部屋の作成・参加画面
  client.ts        対戦画面のクライアント(play/ui.ts の描画部品を流用)
sim2/test/online-*.test.ts
```

**`play/ui.ts` との関係**: 盤面・手札・ログの描画は流用したい。`play/ui.ts` を「描画部品(状態を受け取って描く)」と「ゲーム進行(ローカルでエンジンを回す)」に分けるリファクタをしてよい。既存の人間 vs AI 画面は壊さないこと。

## 3. 隠し情報(view.ts)

サーバーがブラウザに送る状態は、**受け取るプレイヤーごとに作り分ける**。

| 情報 | 自分 | 相手 |
|---|---|---|
| 盤面(式神・向き・ダメージ・マヨヒガ状態) | 見える | 見える |
| 生命・霊力・チップ・制圧状態 | 見える | 見える |
| 手札の中身 | **見える** | **枚数だけ** |
| 山札 | **枚数だけ**(順番は見せない) | 枚数だけ |
| 墓地 | 中身が見える | 中身が見える |
| 乱数の状態(`rngState`) | **送らない** | **送らない** |
| マリガンで戻した札 | 自分の分だけ | 枚数だけ |

**テストで必ず確認すること**: 相手視点のビューをJSONにしたとき、自分の手札の `cardId` と山札の中身と `rngState` が文字列として一切含まれないこと。

イベント(ログ)も同じく作り分ける。相手がドローした札の名前、相手が捨てた札のうち墓地に行く前の選択過程などは相手に送らない(墓地に置かれた札は公開情報なので送ってよい)。

## 4. 試合の進行(match.ts)

### 4.1 手番と入力

- メインフェイズ中は、**手番のプレイヤーだけ**が `action` を送れる。サーバーは `isLegal` で検証し、合法なら `applyActionInPlace` で適用して、両者に更新後のビューとイベントを送る。非合法なら送り主にだけエラーを返す
- ブラウザには、**自分の手番のときだけ合法手の一覧も送る**(`legalActions` の結果)。画面はこれを使ってハイライトする。ブラウザ側で合法判定を持たない
- `pass`(ターン終了)を受けたらサーバーが `endTurn` → 次の `startTurn` まで進める

### 4.2 プレイヤーの選択が必要な場面

エンジンは既に選択を関数で注入できる(`DiscardChooser` / `MulliganChooser` / 古箪笥の `TansuChooser`)。オンラインでは、この関数の中で**サーバーが試合を一時停止し、該当プレイヤーに選択を要求**する。

| 場面 | 誰が選ぶ | 待ち方 |
|---|---|---|
| マリガン | **両者同時**(相手の選択は見えない) | 両者が確定するまで待つ |
| ターン終了時の手札の捨て札 | 手番のプレイヤー | そのプレイヤーの確定を待つ |
| 古箪笥のターン開始時効果 | 古箪笥の持ち主 | 確定を待つ |

エンジンの選択関数は同期関数なので、**「選択待ち状態」をmatch.tsの状態機械で持つ**形にする(例: `endTurn` を呼ぶ前に捨て札を先に集めてから、結果を返す関数を注入して呼ぶ)。エンジン側を非同期化する改修はしない。

### 4.3 ルールの選択

部屋を作る人が選ぶ。

| 設定 | 選択肢 |
|---|---|
| ルール | **9/13テストルール**(既定) / 8/28ルール |
| パック | **shuten-kyuryu**(9/13ルールの既定) / tsukumo-miyako / kyubi-ryu |
| 席 | 先手 / 後手 / ランダム |
| 効果 | on(既定) / off |

「9/13テストルール」「8/28ルール」の中身は、`RESULTS-EXP0913B.md` の定義(K0 と K8ts)と一致させる。**ルールのプリセットは1箇所(例 `src/presets.ts`)に定義**し、CLI・対戦画面・オンラインから同じものを参照する。

### 4.4 切断と放置

- SSEが切れても席は保持する。**同じ席トークンで戻れば続きから**
- 部屋に誰も接続していない状態が **2時間**続いたら部屋を削除
- 手番の時間制限は**設けない**(チームのテスト用途。長考も記録したい)
- 投了ボタンを置く

## 5. 画面(9/13ルールに必要な操作)

既存の人間 vs AI 画面にある操作(召喚・攻撃・回転・霊具・渾身・回復攻撃・代理回転・古箪笥の選択・捨て札)に加えて、**9/13ルールで増えた操作**を作る。これらは既存の対戦画面にも入れること(対戦画面も9/13ルールで遊べるようにする)。

| 操作 | 画面 |
|---|---|
| **継承召喚** | 手札の式神を選ぶと、通常の召喚先に加えて「継承できる自分の式神」を別の色でハイライト。選ぶと、支払い額・回収額・継承後のHPを確認表示してから確定 |
| **マリガン** | 開始時に手札5枚にチェックを付けて「戻す」 |
| **制圧状態** | 盤の脇に「制圧中」の表示。崩れたら消える。自分・相手どちらも |
| **反撃の隙位置** | 範囲攻撃の式神を選んだとき、攻撃範囲(緑)・死角(赤)に加えて**隙位置を別の表示**で出す |
| 撃破した側の霊力獲得 | ログに「撃破により霊力+N」 |

**攻撃前の予測表示**を入れる: 攻撃対象を選んだ段階で、与えるダメージ・反撃の有無・反撃ダメージを表示してから確定する。反撃の条件(隙位置と反撃範囲の両方)は人間には読みにくいので、テストの質を上げるために必要。

## 6. ロビーと招待の流れ

1. 部屋を作る人がロビーでルール・パック・席を選んで「部屋を作る」→ 6文字の部屋コードと招待URL(`/room/ABC123`)が出る
2. その招待URLをLINEで送る
3. 相手が開くと、そのまま席に着く
4. 両者が揃ったらマリガン → 対戦開始
5. 試合終了後「もう一戦(先後入れ替え)」ボタン。同じ部屋で続けて遊べる

観戦(3人目が見るだけ)は**入れる**。観戦者には両者の手札を**見せない**(相手視点と同じ)。テストで3人のうち1人が記録係をするため。

## 7. 公開方法(外からつなぐ)

実装はローカルPCで動くサーバーまで。**外部公開の手段はREADMEに手順を書くだけで、設定作業はしない**。

- 候補A: **Cloudflare Tunnel の一時トンネル**(`cloudflared tunnel --url http://localhost:8788`)。アカウント不要で一時URLが出る。PCを起動している間だけ遊べる
- 候補B: Render / Fly.io などにそのままデプロイ(依存ゼロのNodeアプリなので Dockerfile 1枚で済む)

サーバーは `--port`(既定 **8788**。既存の対戦画面の8787と分ける)と `--host`(既定 `127.0.0.1`、公開時は `0.0.0.0`)を受け取る。

## 8. セキュリティ(最低限)

公開URLで動かすので、これだけは入れる。

- 部屋コードは推測されにくい乱数(`node:crypto` の `randomBytes`)。紛らわしい文字(0/O、1/I/L)を除く
- 席トークンは32バイトの乱数。**プレイヤーの識別はトークンだけで行う**(部屋コードを知っているだけでは他人の席の操作はできない)
- 受け取るJSONは型とサイズを検証する(1リクエスト 16KB まで)。検証に失敗したら 400
- 静的配信はパス走査を拒否する(既存の `play/server.ts` の実装を流用)
- 部屋数の上限(例: 100)と、1IPあたりの部屋作成の頻度制限(例: 1分に5回)
- エラー応答にスタックトレースを含めない

## 9. 受け入れテスト(`node:test`)

1. 部屋を作成し、2人が参加し、席トークンで識別される
2. **相手視点のビューに、自分の手札・山札の中身・`rngState` が含まれない**(JSON文字列を検索して確認)
3. 手番でないプレイヤーの `action` は拒否される
4. 非合法な `action` は拒否され、状態が変わらない
5. 合法な `action` が両者のビューに反映される
6. マリガンは両者の確定を待ってから開始する
7. 捨て札の選択待ちの間、相手の入力は拒否される
8. 席トークンで再接続すると、同じ席の最新ビューが届く
9. 継承召喚がオンライン経由で行え、支払いと回収が正しい
10. 試合終了で棋譜JSONが保存され、**同じシードと同じ入力列で再生すると同じ結果になる**
11. 観戦者は操作できず、手札が見えない
12. 不正なJSON・巨大なリクエストは400
13. 既存のテスト(139件)がすべて通る。既存の人間 vs AI 画面が壊れていない

HTTPを実際に立てるテストは、既存の `play.test.ts` と同じく `createServer` を export してソケットなしでも検証できる形にする。
